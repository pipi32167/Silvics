# 笔记类型与元数据

文档状态：类型层已实现（v0.2.x），日记为第一个类型，剪藏（issue #6）为第二个。

## 0. 为什么要有这份文档

日记是第一个「非普通笔记」的类型，但不会是最后一个（剪藏、书摘、人物、项目都会来）。如果按「加一个 `kind` 值 + 加几列」的方式做，第三次就该还债了。

同时，能被同步的东西不只有 Markdown 正文：日期、URL、抓取时间、别名、忽略过的提及，都要跨设备一致。这些数据放哪、怎么合并、哪些永远不进 vault，必须先定死。

一句话结论：**类型是数据，元数据也是数据，两者都写进文件；数据库只留索引。**

## 2. 类型系统：注册表，不是 enum

`note.kind: note | journal` 只在两个类型时成立。改成 **`type` 字符串 + 类型注册表**：一个类型 = 一个描述符 + 若干解析器，加类型只是加文件。

| 描述符字段 | 作用 | `note` | `journal` | `clip` |
| --- | --- | --- | --- | --- |
| `idRule` | 生成规则，决定跨设备唯一性 | 随机 | 日期派生 `j20261124` | 随机 |
| `path` | vault 内路径 | `notes/<id>.md` | `journal/<date>.md` | `clips/<id>.md` |
| `titleEditable` | 用户能否改标题 | 是 | 否（日期即身份） | 是（原文标题可改） |
| `titleValidation` | 是否套 `validateTitle` | 套 | 跳过 | 跳过。用剪藏自己的清洗（见 `docs/需求-剪藏.md` §7） |
| `linkable` | 能否被 `[[ ]]` 指向 | 是 | 否 | 是 |
| `emitsLinks` | 正文是否解析 `[[ ]]` 产生出边 | 是 | 是 | **否**（单向引用） |
| `isMentionTarget` | 标题是否进提及自动机 | 是 | 否 | **否**（避免噪音） |
| `inMainList` | 是否进「全部」与计数 | 是 | 否 | **否** |
| `inQuickOpen` | 是否进 `⌘P` | 是 | 否 | 否 |
| `countsAsOrphan` | 是否计入孤儿统计 | 是 | 否 | 否 |
| `scanMentions` | 是否跑提及扫描 | 是 | 否（设置可开） | 否 |
| `template` | 新建时注入什么 | 空 | `## 工作` 骨架 | 标题 + 来源 + 摘要 |
| `metaNamespace` | frontmatter 里的类型段 | 无 | `journal:` | `clip:` |
| `editor` | 编辑器形态 | 混合模式 | 混合模式 + 待办 | 同一编辑器只读渲染（`editable=false`，不解析 wiki） |

`emitsLinks`、`isMentionTarget`、`inMainList` 是剪藏引入的字段。判断逻辑必须读描述符，不要再写 `if type == "journal"`。

## 3. frontmatter 契约

### 3.1 分层

```yaml
---
id: j20261124
type: journal
schema: 1
created: 2026-11-24T00:12:03.451Z
updated: 2026-11-24T09:40:11.002Z
status: evergreen
aliases:
  - 遗忘规律
ignoredMentions:
  - n1795488810644ej713s
journal:                    # 类型段：只有 type=journal 的类型读它
  date: 2026-11-24
  carryFrom: 2026-11-23
---
正文……
```

| 层 | 键 | 谁来写 | 说明 |
| --- | --- | --- | --- |
| 身份层 | `id` `type` `schema` | 内核 | 只读，任何类型都不许改 |
| 通用层 | `created` `updated` `status` `aliases` `ignoredMentions` `tags` | 内核 | 所有类型共享。`tags` 用于标签不在正文里的类型（剪藏）；其他类型的标签仍来自正文 |
| 类型层 | `journal:` `clip:` 等命名空间 | 对应类型 | 其他类型不读、不写、不删 |
| 未知层 | 任何不认识的键 | 外部工具 / 未来版本 | **原样保留**，round-trip 不丢 |

### 3.2 三条硬约束

1. **未知键原样保留**。旧版本读到不认识的键，不报错、不丢弃、不改序，写完还是原样。否则新老版本互相踩数据。
2. **序列化稳定**：固定键序（身份层 → 通用层 → 类型层 → 未知层，层内按键名排序）、固定缩进、固定时间格式。同样的值必须产出同样的字节，否则每次同步都是全量 diff，幂等性直接崩。
3. **类型段隔离**：`journal:` 里的键只有 journal 类型解释。删掉一个类型时，它的段落原样留在文件里，不主动清理。

### 3.3 round-trip 用例（实现前先写）

- 含未知键的文件 → 读 → 写 → 字节一致。
- 键序被打乱的文件 → 读 → 写 → 键序归一，内容不变。
- 同值的 `updated` 不同写法（带/不带毫秒）→ 归一化后再比较。

### 3.4 日记模板（`templates/<名字>.md`）

模板不是笔记：它没有 `id` / `title` / `created`，不进 sqlite，也不参与同步合并的笔记去重。
一份模板一个文件，frontmatter 只用 `template:` 段：

```yaml
---
template:
  name: 工作
  order: 1
---
- [ ] 写批次 7 的测试
- [ ] 更新文档
```

- `template.name`：骨架里的标题。缺省取文件名（去掉 `.md`）。
- `template.order`：骨架拼接顺序，数字小的在前；同 order 按名字排。缺省或不是数字的当「排最后」（`Int.max`），只影响排序，不改文件。
- `---` 之后的正文：**会注入骨架**。`⌘⇧J` 新建日记时，每份模板产出 `## <名字>` 加模板正文，段与段之间一个空行。正文里的 `- [ ]` 原样保留，承接逻辑靠它扫未完成项。
- 正文规整只动空行：首尾空行裁掉，连续空行压成一个。不改缩进、不补标点、不改列表前缀。
- 模板没有正文时只写标题，不多出空行。

写入规则：`name` 去首尾空白后不能为空、不能含 `/`；重名拦下；`order` 必须是整数（面板里填错直接报错，不静默回落）。改名时先写新文件再删旧文件，`templates/` 里不留两份。

App 内管理在同一个「模板…」面板（日记工具栏 / 菜单 `日记模板…`）：列表显示名字、order、正文首行摘要，可新建、编辑、删除，勾选决定**下一次新建**用哪些。保存后立即生效：下一次新建读的是磁盘上的最新内容。已有日记正文不受影响。

验收取证：`SILVICS_SHOW=templates` 打开管理面板，`SILVICS_SHOW=templates-result` 用当前模板新建今天的日记。

## 4. 非 Markdown 元数据：四类，四条规则

| 类别 | 例子 | 放哪 | 同步方式 |
| --- | --- | --- | --- |
| ① 类型元数据 | 日记日期、承接来源；剪藏 URL、抓取时间 | frontmatter 类型段 | 随文件走，键级合并 |
| ② 通用元数据 | 标题、状态、别名、忽略项、时间戳 | frontmatter 顶层 | 同上 |
| ③ 二进制资产 | 图片、PDF、附件 | `assets/<sha256>.<ext>` | 内容寻址，天然无冲突 |
| ④ 纯本地状态 | 展开状态、滚动位置、上次同步时间、搜索历史 | 本地 sqlite | **永不进 vault** |

规则：

- 能写成文本的，一律进 frontmatter。文本可 diff、可三方合并、出问题能手改。
- 二进制不 base64 进正文，走旁挂文件 + 内容寻址（同内容同路径，去重、幂等、永不冲突）。
- 本地状态要有白名单，anything not listed 默认视为要同步——反过来做会悄悄丢数据。

二进制资产**本轮不做**，等剪藏（#6）真正需要时再落地；届时约定：

```text
vault/
  assets/<sha256>.<ext>      内容寻址，文件名即校验和
  clips/<id>.md              正文用 ![](assets/<sha256>.png) 引用
```

引用语法沿用标准 Markdown 图片，不发明私有语法。

## 5. 合并策略：frontmatter 与正文分开算

| 段 | 合并方式 | 冲突时 |
| --- | --- | --- |
| frontmatter 标量（status、updated…） | 取 `updated` 较新一侧；`updated` 相同则取两侧相同值 | 值不同 → 冲突，保留本地 + 留档 |
| frontmatter 列表（aliases、ignoredMentions、tags） | 三方集合合并：`base + (local − base) + (remote − base)` | 两边都加 → 都在；一边删一边加 → 保留新增 |
| frontmatter 类型段 | 递归按键合并 | 结构冲突（一边删段一边改）→ 人工 |
| 正文 | 行级 diff3（已实现） | 保留本地 + `.conflicts/` 留档 |

比整文件行合并准，因为 frontmatter 的行序不该带语义。这也要求第 3.2 条的稳定序列化。

## 6. sqlite 的定位

### 6.1 今天

一张库同时干三件事，这是当前最容易出问题的地方。

| 表 | 现在的角色 | 数据 | 可重建 |
| --- | --- | --- | --- |
| `note` | **主存储（真相）** | 正文、标题、状态、时间戳、`bodyHash`、`tags` | —— |
| `alias` | **主存储（真相）** | 别名 | 否 |
| `mention.dismissed` | **主存储（真相）** | 用户忽略过哪些提及 | 否 |
| `link` | 索引 | 引用边与位置 | 是 |
| `tag` | 索引 | `#标签` | 是 |
| `mention`（位置/类型） | 索引 | 提及出现处 | 是 |
| `note_fts` | 索引 | FTS5 trigram，中文子串搜索 | 是 |
| `meta` | 本地状态 | `deviceId` 等 | 否（也不必同步） |

### 6.2 倒转后

| 数据 | 真相在哪 | sqlite 里留什么 |
| --- | --- | --- |
| 正文 | `notes/<id>.md` | 不留（搜索走 FTS） |
| 标题 / 状态 / 别名 / 忽略项 | frontmatter | 只读副本，供唯一索引与筛选 |
| 边 / 标签 / 提及定位 / FTS | 派生 | 索引，重建即恢复 |
| 本地状态 | 本机 | 保留，永不进 vault |

**验收标准：删掉 `silvics.sqlite`，启动后能从 vault 全量重建，内容与操作结果一致。**

### 6.3 表结构变更

```sql
-- v2
ALTER TABLE note ADD COLUMN type TEXT NOT NULL DEFAULT 'note';   -- 取代 kind
ALTER TABLE note ADD COLUMN meta TEXT NOT NULL DEFAULT '{}';     -- 类型段 JSON 镜像（仅索引）
CREATE INDEX idx_note_type ON note(type);

-- v3（剪藏）
ALTER TABLE note ADD COLUMN tags TEXT NOT NULL DEFAULT '[]';      -- JSON 数组，标签不在正文里的类型用它
CREATE INDEX idx_note_tags ON note(tags);
```

`journalDate` 不单独建列：它是 `meta.journal.date`，按类型段解析。理由：每加一个类型就加一列，第三次就散架了。

标签是例外：剪藏标签必须独立存储，因为正文里不写 `#标签`。存 JSON 数组，`tag` 表继续当索引。

manifest 哈希从「正文哈希」改成「整篇哈希」（frontmatter + 正文），manifest `schema: 2`。否则摘要、标签、已读状态变化查不出漂移。

## 7. 保存链路：先写文件，再更新索引

倒转的核心。现在的路径是「改内存 → 写库 → 导出 vault」，倒转后：

```text
1. 计算新正文与新 frontmatter（稳定序列化）
2. 与磁盘上已有文件比较：相同则什么都不做（幂等）
3. 写 <file>.tmp → fsync → replaceItemAt（原子替换）
4. 增量更新索引：link / tag / mention / FTS 只重算这一篇
5. 更新 ui 状态
```

失败处理：

- 第 3 步失败 → 报错、保留旧文件、不更新索引，界面提示「保存失败」。
- 第 4 步失败 → 索引可重建，标记该笔记索引过期，下次启动重算。
- 写文件频率：沿用 500 ms 防抖；`⌘S` 立即写。

## 8. 批次重排（日记 = issue #3）

| 批次 | 内容 | 依赖 | 估时 |
| --- | --- | --- | --- |
| 1 数据层 | `type` + 类型注册表 + `meta` 类型段 + frontmatter 分层与未知键保留 + v2 迁移 | — | 1 天 |
| 2 保存倒转 | 先写文件再更新索引；删库可重建的验收 | 1 | 1–1.5 天 |
| 3 模板与承接 | `templates/<名>.md`；注入骨架；承接上一个有日记的日子，插在当前行前 | 2 | 1 天 |
| 4 编辑器（方案 B） | 光标行露源码、其他行渲染；Home/End、跨行方向键、块元素兜底 | 2 | 2–3 天 |
| 5 代码高亮 | 表驱动词法（5 语言 + 通用 + latex），只加属性 | 4 | 1 天 |
| 6 交叉影响与待办总览 | 日记不进 ⌘P/孤儿/提及（开关）；搜索范围；`⌘⇧J`；`⌘⇧T` 总览 | 3–5 | 1.5 天 |
| 7 收尾 | 文档、截图验收、0.2.0 发布 | 全部 | 0.5 天 |

合计 **8–10 天**。比原计划多两天，多出的是类型注册表与保存倒转。

剪藏（issue #6）不再单建一套类型层，直接复用上面的注册表与保存链路。批次拆分见 `docs/需求-剪藏.md` §17，共 5 个 PR。

## 9. 明确不做

- 通用 block 模型（Notion 式）。正文一旦不是 Markdown，vault、git 合并、外部编辑器全废。
- 二进制 base64 进正文。diff 与合并都会炸。
- 本地状态放进 vault。宁可接受换机器后展开状态丢失。
- 每加一个类型就加一列。
- 主动清理别的类型留下的 frontmatter 段。

## 10. 待定

1. `assets/` 与剪藏的引用语法要不要在 #6 一起定（本轮不做，但约定先写死）。
2. frontmatter 键级合并是否要复用 `LineMerge`，还是单独写 `FrontmatterMerge`（倾向后者，语义不同）。
3. `type` 是否允许用户自定义（例如手写 `type: reading-note` 而不注册），未注册类型按 `note` 处理并给提示。
