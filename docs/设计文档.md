# Evergreen Notes macOS 笔记站 设计文档

版本：v2（技术栈改为 Swift 原生）
状态：待确认

本文用简明技术中文（STC）书写。术语固定：**笔记**（note）、**概念**（concept）、**引用**（link）、**提及**（mention）、**连接**（connection）。

## 1. 目标与边界

### 1.1 产品定义

一个单人使用的 macOS 原生笔记应用。笔记正文是 Markdown 纯文本。用户在正文里写概念名时，应用自动找出这个概念在库内已存在的笔记，并提示建立连接。

核心差异点不是「能写笔记」。核心差异点是**概念引用自动成立**。

### 1.2 范围

| 项 | 结论 |
| --- | --- |
| 平台 | 仅 macOS。不做 Web，不做 iOS |
| 使用者 | 单人 |
| 存储 | 本地 SQLite。离线可用 |
| Markdown 纯文本 + `[[ ]]` | 做 |
| 迁移现有 Obsidian 笔记 | 不做 |
| 公开分享页 | 不做 |
| 云端多设备同步 | 后续阶段。数据层预留接口 |
| LLM 与 embedding | 支持常见服务商，BYOK（用户自带 key） |
| 知识图谱 | 做（P5） |

### 1.3 量级假设

笔记总数不少于 1000 条。单条正文 200 至 800 字。标题 4 至 40 字。中文为主，混英文术语。

## 2. Evergreen Notes 的设计内核

### 2.1 Matuschak 的五条原则

这五条不是风格偏好。它们是对产品的硬约束。

| 原则 | 原文含义 | 对产品的约束 |
| --- | --- | --- |
| 原子 | 一条笔记只装一个概念 | 必须阻止长笔记。设字数软上限 |
| 概念导向 | 笔记属于概念，不属于书或日期 | 禁止日期标题、禁止以书名当标题 |
| 密集链接 | 链接要多 | 建链接的成本必须接近零。这是自动化的理由 |
| 联想式组织 | 不用层级分类法 | 不提供文件夹。只提供标签与图 |
| 写给自己 | 不预设读者 | 不设置发布流程、不设置协作权限 |

### 2.2 最关键的隐含约定：标题即接口

Matuschak 的笔记标题写成完整断言句。

例：`稀疏重复优于集中突击`、`写作是最有效的思考方式`、`理解需要费力参与`。

不是 `读书笔记 3`，不是 `2026-10-31`。

这个约定同时满足两件事：

1. 标题能在别的笔记正文里当作自然语言句子使用。
2. 因为可被当作句子使用，机器才能定位它，从而生成连接。

**结论：自动连接能否成立，取决于标题是否可识别。** 大多数笔记应用做不好自动连接，根因就是标题是任意字符串，无法被正文自然引用。

这一条直接决定界面设计：新建笔记的标题输入框必须有引导和校验。详见 5.1。

### 2.3 参照产品与取舍

| 产品 | 做法 | 借鉴 | 不借鉴 |
| --- | --- | --- | --- |
| notes.andymatuschak.org | 无侧栏。反向链接内联在正文下方，带上下文片段 | 反向链接的呈现方式。这是最高价值的一处 | 无搜索 |
| Obsidian | 文件即真相。`[[ ]]`。反向链接 + 未链接提及 | 数据格式与心智模型 | 文件夹树。自动连接靠插件，默认不生效 |
| Roam / Logseq | 块级大纲。块引用 | 无 | 块引用导致概念碎片化，难形成断言句 |
| Bear | 原生 NSTextView。混合式 Markdown 样式 | 编辑器手感与渲染策略 | 无引用与反向链接 |
| Supernotes | 卡片强制原子 | 用物理约束强制原子性 | 卡片墙视图不适合长概念 |
| Tana | 超级标签与结构化字段 | 无 | 学习成本过高 |

### 2.4 用「阻碍」塑造习惯

产品不能只提供能力。产品要设计阻力。

| 阻力 | 实现 |
| --- | --- |
| 阻止写长笔记 | 正文超过 800 字，编辑区顶部出现「建议拆分为 N 条」提示 |
| 阻止日期标题 | 标题形如日期时拒绝，并给示例句 |
| 阻止重复概念 | 标题输入时实时查重，显示相似度最高的 3 条已有笔记 |
| 阻止孤立笔记 | 侧栏常驻「孤儿笔记」入口 |

## 3. 自动连接的四层机制

这是本产品的核心设计。

### 3.1 分层原则

连接分两种性质：**硬连接**（可确定验证）与**软连接**（推测）。

两者必须在界面、数据结构、视觉上完全分开。混淆一次，用户就不再相信整个连接层。

**铁律：L3 与 L4 永不改写用户正文。** 只做建议。

### 3.2 L1：显式引用

| 项 | 定义 |
| --- | --- |
| 语法 | `[[标题]]`、`[[标题\|显示名]]`、`[[标题#小标题]]` |
| 可靠性 | 确定。字符串精确匹配 |
| 解析结果 | 建一条有向边。目标笔记上出现一条反向链接 |
| 悬空目标 | 目标不存在时，边标记为 `dangling`。正文显示灰色虚线。点击可新建 |

解析不走通用 Markdown 解析器。理由见 8.3。

### 3.3 L2：未链接提及

| 项 | 定义 |
| --- | --- |
| 触发 | 正文里出现的字符串，等于库内某条笔记的标题或别名 |
| 可靠性 | 确定。纯字符串匹配，无推测 |
| 输出 | `Mention { noteID, targetID, offset, length, kind }` |
| 界面 | 原文该字符串加淡色下划线。光标进入时浮出「提及《X》，转为引用？」 |
| 批量操作 | 侧栏列出全部提及。支持全选转换。转换前给 diff 预览 |
| 排除区 | 代码块内、行内代码内、已是引用的区间内、URL 内 |

**匹配规则（按置信度降序）：**

1. `kind = exact`：正文片段完全等于笔记标题。置信度高。
2. `kind = alias`：正文片段完全等于笔记别名。置信度高。
3. `kind = partial`：标题包含正文片段，或正文片段包含标题。置信度中。默认不自动提示，只在侧栏列出。

**中文特有约束：**

中文没有词边界，子串匹配误报高。加三条门槛：

1. 匹配片段长度不小于 4 个汉字（英文不小于 2 个词）。
2. 匹配片段不能落在停用词表内。
3. 同一目标在单篇笔记内出现超过 20 次时，只报一次。

### 3.4 L3：概念抽取与建议新概念

| 项 | 定义 |
| --- | --- |
| 目标 | 找出正文里「应该是一条笔记」但库里还没有的概念 |
| 可靠性 | 中。需要人工确认 |
| 纯本地路径 | `NLTokenizer(unit: .word)` 分词（系统自带，中文分词实测有效）、停用词过滤、词频排序、与库内标题模糊匹配 |
| LLM 增强路径 | 把当前笔记正文 + **库内全部标题清单**发给模型。模型只能从清单中选择 |
| 强制约束 | 模型不能自由生成链接目标。目标必须来自给定标题清单或用户手动确认。否则产生悬空引用与幻觉 |
| 界面 | 侧栏「概念线索」区。每条建议带「建立引用」「新建笔记」「忽略」三个动作 |

分词实测结果（本机 macOS 26.5，Swift 6.3）：

```text
输入：稀疏重复优于集中突击，但遗忘曲线决定了长期留存。间隔重复能对抗遗忘。
输出：稀疏 | 重复 | 优于 | 集中 | 突击 | 但 | 遗忘 | 曲线 | 决定 | 了 | 长期 | 留存 | 间隔 | 重复 | 能 | 对抗 | 遗忘
```

分词正确，无需引入第三方分词库。

### 3.5 L4：语义近邻

| 项 | 定义 |
| --- | --- |
| 目标 | 发现措辞不同但主题相近的笔记 |
| 可靠性 | 低。纯推测 |
| 向量来源 | **必须云端 BYOK**。理由见 8.5 实测 |
| 输入 | 标题 + 正文。正文超长时分块，取均值向量 |
| 存储 | 向量存 SQLite（BLOB）。只对正文哈希变化的笔记重算 |
| 阈值 | 余弦相似度大于 0.82 才展示 |
| 界面 | 侧栏「相关笔记（推测）」。附理由：共享关键词列表 |
| 硬约束 | 不进正文。不进主图。不计入连接统计 |

### 3.6 四层总表

| 层 | 名称 | 可靠性 | 是否改正文 | 是否进图 | 何时计算 |
| --- | --- | --- | --- | --- | --- |
| L1 | 显式引用 | 确定 | 是（用户手动） | 是，实线 | 保存时增量 |
| L2 | 未链接提及 | 确定 | 否（一键转） | 否 | 停止输入后 500 ms |
| L3 | 概念抽取 | 中 | 否 | 否 | 手动触发或空闲时 |
| L4 | 语义近邻 | 低 | 否 | 否 | 后台增量 |

## 4. 数据模型

### 4.1 核心决定：正文是唯一真相

连接不持久化为真源。真源是笔记正文的 Markdown 文本。

连接表、提及表、向量表都是**索引**。索引可以随时从正文重建。

原因：用户只编辑文本。任何独立的连接表都会与文本漂移，产生「图里有边，正文里没有」的经典缺陷。

### 4.2 表结构

存储用 GRDB（SQLite）。

```sql
CREATE TABLE note (
  id           TEXT PRIMARY KEY,        -- ULID
  title        TEXT NOT NULL,           -- 必须是完整断言句
  body         TEXT NOT NULL,           -- Markdown 纯文本，真源
  status       TEXT NOT NULL DEFAULT 'seedling',  -- seedling|budding|evergreen
  created_at   INTEGER NOT NULL,
  updated_at   INTEGER NOT NULL,
  body_hash    TEXT NOT NULL            -- 判定是否需要重算索引
);

CREATE TABLE alias (
  note_id  TEXT NOT NULL REFERENCES note(id) ON DELETE CASCADE,
  name     TEXT NOT NULL,
  PRIMARY KEY (note_id, name)
);
CREATE INDEX idx_alias_name ON alias(name);

CREATE TABLE tag (
  note_id  TEXT NOT NULL REFERENCES note(id) ON DELETE CASCADE,
  name     TEXT NOT NULL,
  PRIMARY KEY (note_id, name)
);

-- 索引：从正文解析出的边
CREATE TABLE link (
  id           INTEGER PRIMARY KEY,
  from_id      TEXT NOT NULL REFERENCES note(id) ON DELETE CASCADE,
  to_id        TEXT,                    -- NULL 表示悬空
  raw_target   TEXT NOT NULL,           -- [[ ]] 内原文
  display_text TEXT NOT NULL,
  anchor       TEXT,                    -- #小标题
  offset       INTEGER NOT NULL,
  length       INTEGER NOT NULL,
  status       TEXT NOT NULL            -- resolved|dangling
);
CREATE INDEX idx_link_from ON link(from_id);
CREATE INDEX idx_link_to   ON link(to_id);
CREATE INDEX idx_link_raw  ON link(raw_target);

-- 索引：未链接提及
CREATE TABLE mention (
  id         INTEGER PRIMARY KEY,
  note_id    TEXT NOT NULL REFERENCES note(id) ON DELETE CASCADE,
  target_id  TEXT NOT NULL REFERENCES note(id) ON DELETE CASCADE,
  offset     INTEGER NOT NULL,
  length     INTEGER NOT NULL,
  kind       TEXT NOT NULL,             -- exact|alias|partial
  dismissed  INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_mention_note ON mention(note_id);

-- L4 向量
CREATE TABLE embedding (
  note_id    TEXT PRIMARY KEY REFERENCES note(id) ON DELETE CASCADE,
  vector     BLOB NOT NULL,
  model      TEXT NOT NULL,
  dim        INTEGER NOT NULL,
  body_hash  TEXT NOT NULL
);
```

全文搜索用 FTS5 外部内容表：

```sql
CREATE VIRTUAL TABLE note_fts USING fts5(
  title, body,
  content='note', content_rowid='rowid',
  tokenize='trigram'
);
```

`trigram` 分词器已在本机验证。中文子串搜索可用：

```text
输入：稀疏重复优于集中突击，遗忘曲线决定长期留存
查询 MATCH '集中突击' → 命中 1 条
```

选 `trigram` 不选 `unicode61`。理由：中文无空格，`unicode61` 需要预处理插空格，且无法支持长度大于 3 字的子串匹配。

### 4.3 索引重算流程

```text
保存笔记 N
  ├─ body_hash 未变 → 跳过
  └─ body_hash 变化
       ├─ 扫描 N.body 的 [[ ]]，diff 出边，重写 link（where from_id = N）
       ├─ 扫描 N.body 的提及，重写 mention（where note_id = N）
       ├─ 更新 note_fts
       └─ 标记 N 的 embedding 待重算

标题或别名变更
  ├─ 重算全部 link 的 to_id 与 status（悬空 ↔ resolved）
  └─ 全库重算 mention（后台任务，显示进度）

新建或删除笔记
  └─ 同上，按标题变更处理
```

性能预算：1000 条笔记，全库提及重算不超过 300 ms。

## 5. 界面设计

### 5.1 新建笔记（守门）

```text
┌────────────────────────────────────────────┐
│ 新笔记                                      │
│                                            │
│ 标题                                       │
│ ┌────────────────────────────────────────┐ │
│ │ 稀疏重复优于集中突击                      │ │
│ └────────────────────────────────────────┘ │
│ 提示：标题写成一句可读的断言。不要写日期。      │
│                                            │
│ 相似笔记（避免重复）                          │
│ · 集中突击会造成疲劳          相似度 0.71  →  │
│ · 复习间隔应随记忆强度调整     相似度 0.64  →  │
│                                            │
│                          [取消]  [创建笔记]  │
└────────────────────────────────────────────┘
```

标题校验规则：

1. 长度 4 至 40 字。少于 4 字拒绝。
2. 形如 `2026-10-31`、`10月31日`、`第 3 章` 时拒绝。
3. 以 `读书笔记`、`会议记录`、`TODO` 开头时警告。
4. 与已有标题规范化后完全相同时拒绝。

### 5.2 编辑器（写作主界面）

```text
┌──────────┬─────────────────────────────┬──────────────┐
│ 搜索      │  稀疏重复优于集中突击          │ 反向链接 (12) │
│ ─────    │  [seedling ▾]  #记忆 #学习    │ · 复习间隔…   │
│ 最近       │                             │   "…稀疏重复…" │
│ 孤儿 (7)   │  集中突击可以短期记住更多，     │ · 高效学习的…  │
│ 随机       │  但[[遗忘曲线]]决定了长期留存。  │   "…对抗遗忘…" │
│ 标签       │  因此[[间隔重复]]更有效。       │              │
│           │                             │ 提及 (3)      │
│ 全部 (1042)│  遗忘曲线说明了这一点。← 淡下划线│ · 遗忘曲线 →   │
│           │                             │ · 主动回忆 →   │
│           │                             │              │
│           │                             │ 相关 (推测)    │
│           │                             │ · 检索练习     │
└──────────┴─────────────────────────────┴──────────────┘
```

三栏用 `NavigationSplitView`。

关键交互：

1. 输入 `[[` 立刻弹出补全浮层。列表按「标题前缀匹配 → 标题包含 → 正文包含 → 语义近邻」排序。每项显示标题、状态、被引用次数。
2. 无匹配时，列表首项是「新建《所输文字》」。回车直接建笔记并插入引用。
3. 光标落在未链接提及上时，浮出快捷键提示。按 `⌘⇧K` 转为引用。
4. 反向链接带原文上下文片段。这是 Matuschak 站点的做法。片段比标题列表有用得多。
5. `⌘P` Quick Open 全部笔记。`⌘⇧O` 列出孤儿笔记。

### 5.3 提及整理（批量）

```text
┌──────────────────────────────────────────────┐
│ 未链接提及  12 条     [全选]  [全部转换]        │
│ ────────────────────────────────────────────  │
│ ☑ 《遗忘曲线》 出现在 3 篇笔记                  │
│    稀疏重复优于集中突击                         │
│    "…[[遗忘曲线]]决定了长期留存。"              │
│    转换后将插入 1 个引用                        │
│ ────────────────────────────────────────────  │
│ ☐ 《间隔重复》 出现在 2 篇笔记                  │
│    …（partial 匹配，置信度中）                  │
│                              [查看 diff] [转换] │
└──────────────────────────────────────────────┘
```

批量转换必须先看 diff。转换是不可逆的文本改动，用户要能预判。

### 5.4 视觉分层规则

| 元素 | 表现 |
| --- | --- |
| 有效引用 `[[ ]]` | 方括号淡灰，标题文字主题色 + 下划线 |
| 悬空引用 | 灰色虚线，点击新建 |
| 未链接提及 | 淡色点状下划线。悬停变实线 |
| L3 建议 | 侧栏内。带虚线图标 |
| L4 推测 | 侧栏内。带「推测」标签，无可视强调 |

### 5.5 系统能力（原生白送）

选原生技术栈的核心收益。以下能力不需要写代码：

| 能力 | 来源 |
| --- | --- |
| 系统查找栏（`⌘F`） | `NSTextView.usesFindBar` |
| 拼写与语法检查 | `NSTextView` |
| 听写 | 系统 |
| 文本替换与智能引号 | `NSTextView` 自动 |
| 表情与符号面板 | 系统 |
| 服务菜单、Look Up、翻译 | 系统 |
| 辅助功能（VoiceOver） | 系统 |
| 撤销与重做 | 自管 `EditorUndoStack`（issue #35）。`NSTextView` 的撤销分组在真实事件循环里不闭合，整场输入会合成一步，`⌘Z` 一次清空整篇，不能用 |
| 全屏、窗口标签、状态恢复 | AppKit |
| 拖放文本与文件 | AppKit |
| 系统深浅色 | SwiftUI / AppKit |
| 中文输入法 | 系统 IME |

Web 方案下这些全部要重新实现，且质量不及系统。

## 6. 为什么不用 Web 技术

结论：macOS 上用 WKWebView 做不到原生笔记应用的手感。核心原因是文本输入，不是渲染。

### 6.1 证据

| 证据 | 说明 |
| --- | --- |
| CodeMirror 仓库 issue #1409 | macOS 原生中文输入法下，候选词窗口位置错误 |
| CodeMirror 仓库 issue #1650 | 在语法高亮节点边界处进行中文输入法组合时，正文被破坏。issue 描述为可靠复现 |
| VS Code PR #333909 | WebKit 下中文输入法抖动。VS Code 需要专门修隐藏 textarea 层的滚动对齐 |
| SoloMD 放弃 CodeMirror | 中文输入丢字、标点要按两次。最终把 Windows 编辑器从 CodeMirror 换成原生块编辑器 |
| 设计层面 | WKWebView 拿不到第 5.5 表中的任何一项系统能力 |

### 6.2 为什么 Tauri / Electron 也不够

Tauri 体积小、启动快。但它仍然是 WKWebView 加 Rust 外壳。文本编辑仍然走 Web 的输入管线。

对一个每天输入中文数千字的应用，这条差异每天都摸得到。渲染差距可以忽略，输入差距不能。

### 6.3 成本

| 项 | Web 方案 | Swift 方案 |
| --- | --- | --- |
| 启动成本 | 低。Vite 起手即可 | 中。需要 Xcode 项目、AppKit 知识 |
| 编辑器手感 | 中。CodeMirror 已很强 | 高。原生 |
| 中文输入 | 有已知缺陷 | 系统级正确 |
| 系统集成 | 需逐项重写 | 白送 |
| 分发 | 静态托管 | 需 Xcode 构建 |

单人自用、无 Web 分发需求、每天长时间输入中文。Swift 方案的净收益为正。

### 7.1 主栈

| 层 | 选择 | 理由 |

### 7.2 明确不用的库

| 库 | 不用的理由 |
| --- | --- |
| STTextView | GPLv3 或商业授权双许可。自用无碍，但引入授权约束。它是源码编辑器组件，带行号与 gutter，笔记应用不需要。原生 `NSTextView` 更合适 |
| SwiftData | 无 FTS。复杂查询与迁移能力弱于 GRDB |
| CodeMirror / Milkdown / TipTap | 见第 6 章 |

| 第三方 Markdown 编辑器框架 | 无成熟的 Swift 版 |

### 7.3 为什么不用 STTextView

`STTextView` 是活跃项目（122 个 release，4 年维护），质量不低。但：

1. 授权是 GPLv3 或商业授权。个人自用可以，但一旦想开源或分发就受限。
2. 它面向源码编辑器。行号、gutter、代码折叠是主要卖点。笔记应用都不要。
3. 原生 `NSTextView` 白送第 5.5 章全部系统能力。`STTextView` 是重实现，部分能力缺失。

结论：用原生 `NSTextView`。

### 7.4 Markdown 渲染策略与解析器

#### 编辑区内的样式策略

这是本项目最大的技术取舍。三个方案：

| 方案 | 做法 | 风险 | 结论 |
| --- | --- | --- | --- |
| A 语法保留 + 样式化 | `**粗体**` 星号保留可见但淡灰，文本加粗；`[[X]]` 方括号淡灰，`X` 主题色 | 零布局风险。光标位置绝对准确。中文输入安全 | **P1 采用** |
| B 语法隐藏（Obsidian live preview） | 非光标行隐藏语法标记，需零宽 glyph 替换 | `NSTextView` 下需自定义 layout manager 的 fragment 处理。光标位置、选区、复制、中文输入组合期都要单独处理 | P2 实验，可开关 |
| C 分屏预览 | 左写右看 | 违背「纯文本即真相」的认知 | 不做 |

选 A 的理由：文本布局不改变，光标位置不会错，中文输入法组合不会被打断。实现量约 300 行。观感是 Bear 的混合模式，用户接受度高。

选 B 的诱因是好看。但代价是重新解决一堆已在 Web 侧被证明难缠的问题（见 6.1）。P1 不碰。

#### 解析器分工

方案 A 需要知道「哪些字是粗体」「哪些字是引用」，才能套属性。分工如下：

| 语法 | 解析方 | 理由 |
| --- | --- | --- |
| `[[ ]]` 引用 | **自写 WikiScanner** | cmark 不认识这个语法。自写才能拿到精确区间 |
| `#` 标题、`**` 粗体、`*` 斜体、行内代码、`>` 引用块、列表 | **`swift-markdown`** | 正确性由 cmark-gfm 保证，不自造轮子 |
| `#tag` 标签 | 自写（简单行内规则） | cmark 把 `#tag` 当纯文本或标题，不可控 |
| 导出与预览渲染 | `swift-markdown` | 正确性优先 |

两条解析路径互不干扰。实测确认：cmark 把 `[[遗忘曲线]]` 当纯文本处理，不产生 Link 节点，也不影响后续 `**粗体**` 的区间。

#### 实测：`swift-markdown` 的区间偏移单位是 UTF-8 字节

这是必须写进代码注释的坑。`SourceLocation.column` 跟的不是字符，也不是 UTF-16，是 **UTF-8 字节**。

实测环境：macOS 26.5，Swift 6.3，swift-markdown 0.4+。输入含中文与 `[[ ]]` 的笔记，`**长期留存**` 的区间是 `3:68-3:84`：

| 把 column 当何种单位 | 取出的文本 | 正确 |
| --- | --- | --- |
| 字符（`String.count`） | `忘曲线]]决` | 错 |
| UTF-16（`String.utf16.count`） | `忘曲线]]决` | 错 |
| **UTF-8 字节（`String.utf8.count`）** | **`**长期留存**`** | **对** |

按 UTF-8 映射后，Heading、Strong、InlineCode、Link、BlockQuote、ListItem、Text 七类节点的区间全部准确。按字符映射则整篇中文笔记全部错位。

实现要点：

1. 建立行起始的 **UTF-8 字节偏移数组**。不要用 `String.count`。
2. 换行判定扫 `utf8` 视图里的 `0x0A`。
3. `NSRange` 要的是 UTF-16 单位。字节偏移需再转一次：`utf8` 定位 → `String.Index` → `utf16.distance`。
4. 调用 `NSTextStorage.addAttributes(_:range:)` 时，区间必须是 UTF-16 的 `NSRange`。

#### 标题字符限制

标题禁止包含 `[`、`]`、`(`、`)`。理由：`[[A](B)]]` 会被 cmark 解析成链接，破坏区间。新建笔记时校验这条。

#### 解析耗时实测

正文 805 字（1693 字节），release 构建，同一台机器：

| 操作 | 耗时 | 结论 |
| --- | --- | --- |
| `swift-markdown` 全量解析 + 遍历 | **0.246 ms** | 每次输入全量重解析也够快 |
| UTF-8 行索引构建 | 0.002 ms | 可忽略 |
| 自写 `[[ ]]` 扫描 | 0.001 ms | 可忽略 |

结论：**不做增量解析**。全量重解析加全量套属性在 1 ms 量级，比维护增量状态的复杂度便宜得多。只对超长笔记（超过 5000 字）做段落级增量。

### 8.2 编辑器桥接

```swift
struct NoteEditor: NSViewRepresentable {
    @Binding var text: String
    let decorations: EditorDecorations   // 引用、提及、悬空指向的区间

    func makeNSView(context: Context) -> NSScrollView { … }
    func updateNSView(_ view: NSScrollView, context: Context) { … }
}
```

要点：

1. `NSTextView` 放在 `NSScrollView` 内，`isRichText = false`，`allowsUndo = true`，`usesFindBar = true`。
2. 关闭 `isAutomaticQuoteSubstitution`、`isAutomaticDashSubstitution`。Markdown 里这些会破坏语法。
3. 关闭 `isAutomaticTextReplacement`。避免自动改用户写的中文。
4. 属性应用通过 `NSTextStorage.beginEditing()` / `endEditing()` 包起来，一次提交。
5. **只重扫变更段落。** 用 `NSTextStorage.editedRange` 与 `delta` 定位。全量重扫只在打开笔记时做。

### 8.3 WikiScanner

不依赖 `swift-markdown`。理由：

1. 编辑器需要的是**字符区间**，不是 AST。`[[X]]` 在文本里的位置直接喂给 `NSTextStorage` 才有效。
2. `swift-markdown` 的自定义语法扩展能力有限。社区有专文讨论其局限。
3. 扫描器比 AST 快一个数量级，可在输入时反复运行。

扫描器约 100 行。规则：

| 规则 | 处理 |
| --- | --- |
| 跳过 fenced code block | 按行跟踪 ` ``` ` 开闭 |
| 跳过行内代码 | 配对反引号计数 |
| 跳过已有 URL | 前缀 `://` 检测 |
| 支持 `[[X]]` | target = X |
| 支持 `[[X\|显示名]]` | target = X，display = 显示名 |
| 支持 `[[X#小标题]]` | target = X，anchor = 小标题 |
| 未闭合的 `[[` | 忽略，不产生链接 |

导出与预览路径才用 `swift-markdown`。用法：先把 `[[X]]` 替换成标准 Markdown 链接 `[X](note://<id>)`，再交给 cmark-gfm 解析。这样渲染正确性由 cmark 保证，引用语法自己掌控。

### 8.4 提及扫描：必须用 Aho–Corasick

原计划是「先朴素匹配，实测超标再上 Aho–Corasick」。实测结果是直接超标 10 倍。方案改为 P2 一开始就写 Aho–Corasick。

实测条件：正文 805 字，1003 个标题（含别名），release 构建。

| 方案 | 耗时 | 相对朴素 | 结论 |
| --- | --- | --- | --- |
| 朴素 `String.range(of:)` 逐标题匹配 | **214.1 ms** | 1× | 不可用 |
| 二元组预筛 + 朴素匹配 | **2.685 ms** | 80× 快 | 可用，但只是退路 |
| **Aho–Corasick 扫描** | **0.099 ms** | **2163× 快** | **采用** |
| Aho–Corasick 构建（1003 标题，一次性） | 2.216 ms | — | 仅在标题集合变化时重建 |

自动机规模：1003 个标题共 6014 个节点。常驻内存可忽略。

实现要点：

1. 按 Unicode 标量构建转移表。键用 `[UInt32: Int]`，中文标量直接作键。
2. 大小写与全半角归一化在插入时做，扫描时不再做。
3. `out` 数组沿 fail 链合并，保证重叠命中全部报出。
4. 扫描时记录 `endOffset` 与 `patternIndex`，用 `endOffset - titleLength` 反推起点。
5. 命中后过滤三类区间：代码块、行内代码、已是引用的区间。区间集合由 7.4 的解析结果提供。
6. 中文三条门槛仍生效：
   1. 长度不小于 4 汉字。
   2. 不在停用词表内。
   3. 单篇同目标上限 20 次。

调用时机：停止输入 500 ms 后。0.099 ms 的扫描成本允许更高频，但没必要。

「二元组预筛」保留为退路。Aho–Corasick 写错（尤其是 fail 链与重叠命中）时的替代方案，2.685 ms 也在预算内。

### 8.5 L4 向量来源：本机实测结论

**`NLEmbedding` 的中文句向量不可用于 L4。** 实测数据：

查询：`如何用间隔重复对抗遗忘曲线`
模型：`NLEmbedding.sentenceEmbedding(for: .simplifiedChinese)`，640 维

| 候选句 | 相似度 | 应然 |
| --- | --- | --- |
| 复习间隔应随记忆强度动态调整 | 0.9708 | 相关 |
| 稀疏重复优于集中突击 | 0.9600 | 相关 |
| 集中突击会造成记忆疲劳 | 0.9454 | 相关 |
| **今天中午吃了牛肉面** | **0.9405** | **无关** |
| 猫咪喜欢晒太阳 | 0.9273 | 无关 |
| SwiftUI 的 NavigationSplitView 用法 | 0.8325 | 无关 |

无关句 0.9405，相关句 0.9454。差距 0.005。阈值无法设定。

词向量平均略好：

| 候选句 | 相似度 |
| --- | --- |
| 复习间隔应随记忆强度动态调整 | 0.5888 |
| SwiftUI 的 NavigationSplitView 用法 | 0.4847 |
| 集中突击会造成记忆疲劳 | 0.4858 |
| 稀疏重复优于集中突击 | 0.4578 |
| 猫咪喜欢晒太阳 | -0.0812 |
| 今天中午吃了牛肉面 | -0.2089 |

有区分度，但「SwiftUI 用法」排在两个相关句之间。误报仍高。

**结论：**

1. L4 主力必须是云端 BYOK embedding。推荐模型：`text-embedding-3-large`、`bge-m3`、`qwen3-embedding-8b`、`jina-embeddings-v3`、`voyage-3`。
2. `NLEmbedding` 只做「无网络时的降级」，且默认关闭。界面必须标明「离线近似，误报高」。
3. 这也说明：L4 永远只能是建议层，不能进正文与主图。第 3.1 章的分层原则由实测数据支持，不是保守。

### 8.8 保存策略

```text
编辑 → 防抖 500 ms → 写内存模型 → 后台队列写 GRDB
⌘S   → 立即 flush
笔记切换 / 窗口失焦 / 应用退出 → 强制 flush
```

不用 `NSDocument`。理由：笔记是数据库记录，不是独立文件。`NSDocument` 的「打开文件」模型与 1000 条笔记的库模型冲突。

要有崩溃保护：`applicationWillTerminate` 与 `NSApplication.willResignActiveNotification` 都触发 flush。

## 10. 风险与对策

| 风险 | 后果 | 对策 |
| --- | --- | --- |
| 自动连接误报 | 用户不再信任连接层 | 四层分级。L3 与 L4 永不改正文，永不进主图 |
| LLM 编造链接目标 | 产生大量悬空引用 | 模型只能从给定标题清单中选择。目标必须可校验 |
| 中文子串匹配误报 | 提及列表全是噪音 | 三条门槛：长度不小于 4 汉字、不在停用词表、单篇上限 20 次 |
| 正文与索引漂移 | 图与正文不一致 | 正文是真源。索引可从正文全量重建。设置里提供「重建索引」 |
| 标题改名 | 大量引用变悬空 | 别名机制 + 改名时自动批量重写正文引用 |
| 笔记超过 1000 条后性能下降 | 卡顿 | 标题集合常驻内存。提及按需计算。图只渲染局部 |
| 笔记膨胀成文章 | 失去原子性 | 字数软上限 + 拆分提示 |
| 重复笔记 | 概念分裂 | 新建时实时查重，显示相似度前 3 |
| TextKit 2 布局缺陷 | 光标跳动、行高异常 | 保留降级开关：`NSTextView` 可强制回 TextKit 1 |
| 语法隐藏（方案 B）破坏中文输入 | 输入丢字或乱序 | P1 不做方案 B。P2 做时必须带开关与回归测试 |
| Keychain 与沙盒冲突 | 读取 key 失败 | 不开沙盒 |
| `NLEmbedding` 中文质量差 | L4 全是误报 | 实测已证。离线模式默认关闭 |

### 11.1 应用名与 bundle id

**已定：`Silvics`**

Silvics 是林业术语，指研究林木生命史、生长与生态的学科（如美国农业部《Silvics of North America》）。选它的理由：

2. 6 字母，小写连写辨识度高，好念（/ˈsɪlvɪks/）。
3. 软件产品里无同名占用。同名的是学术出版物，领域正交。
4. 与「菌网」的隐喻同源：菌根正是林木生长所依赖的地下网络。Silvics 覆盖地上，菌网覆盖地下。

显示名：`Silvics`
数据库文件名：`silvics.sqlite`

候选方案两个：
