# 双客户端冲突测试：多设备改同一篇笔记

场景：两台设备各自改了同一篇笔记的同一段，同步时 diff3 合不了。要求用本地 LLM（magpie 的 DeepSeek 路由组）合并，人工确认后落库。

## 环境

| 项 | 值 |
| --- | --- |
| LLM 入口 | magpie 本地代理 `http://127.0.0.1:3425/v1`（OpenAI 兼容，免密钥） |
| 模型 | `auto/deepseek-v4.1-flash`（routing group） |
| 合并实现 | `EditorKit/LineMerge`（diff3）→ 冲突时 `Core/ConflictResolver` + `Core/ChatClient` |
| 复现脚本 | `scripts/conflict-drill.sh`（DEBUG 版 App 内的 `SILVICS_CONFLICT_DRILL=1`） |

## 演练步骤

1. 建裸仓 `remote.git`，克隆出 `deviceA`、`deviceB`。
2. 两边写入同一篇笔记基线：

   ```text
   第一段：这是共同基线。
   第二段：间隔重复优于集中突击。
   第三段：结尾。
   ```

3. `deviceA` 把第二段改成「……但每天只能练 20 分钟」，提交并 push。
4. `deviceB` 把同一段改成「……前提是总时长相同」，提交后 fetch。
5. 用 `LineMerge.merge(base:ours:theirs:)` 复现冲突。
6. 把三方正文交给 `ConflictResolver`（模型走 magpie）。
7. 校验返回：非空、无冲突标记、无代码围栏、长度不超过 3 倍、与本机版本不同。

## 实测结果（2026-11-24）

```text
[drill] 两台设备改了同一段
[drill] LineMerge 干净合并: false 冲突数: 1
[drill] LLM 合并成功 (2695 ms)：
第一段：这是共同基线。
第二段：间隔重复优于集中突击，前提是总时长相同，但每天只能练 20 分钟。
第三段：结尾。
```

界面路径（设置里绑定 magpie 后）：「处理同步冲突…」（`⌘⇧C`）→ 选中冲突 →「用 LLM 合并这篇」→ 看 diff →「采用结果」。

第二次界面实测（`SILVICS_CONFLICT_DEMO=1`）的合并结果：

```text
第一段：写作工具的核心指标是每次开口的摩擦。
第二段：间隔重复优于集中突击，前提是总时长相同，但每天只能练 20 分钟。
第三段：结论先写下来，再补理由。
待定：本机版本的「每天只能练 20 分钟」与远端版本的「前提是总时长相同」是否同时成立，需确认二者是否为同一约束。
```

diff 只显示两处变化（冲突行 + 新增「待定」行），未冲突的第一段、第三段逐字保留。

## 踩到的问题

1. **模型会照抄提示词里的分隔标记。** 第一版返回 `标题：…`、`【共同基线】`、`【远端版本】`。修法两条：提示词加「输出里不得出现这些标记」，并在 `ConflictResolver.clean` 里逐行丢弃。
2. **模型会重写未冲突的行。** 第一版把「第一段：」「第三段：」前缀删掉了。提示词补第 7 条：未冲突的行必须逐字保留，包括行首前缀。
3. **magpie 没有 embedding 接口。** `POST /v1/embeddings` 返回 404，所以 L4（相关笔记）不能走 magpie，只有 L3 可用。

## 结论与边界

- 这个流程只解决**同一文件被两边改**的情况。标题两边都改、远端删除本地有改动，仍然只提示、不自动处理。
- 合并结果是**建议**：必须人工确认才写回。原始三方版本已由 `VaultSync` 留档在 `.conflicts/`。
- magpie 的 `auto/*` 是路由组，实测响应头 `X-Magpie-Provider` 会告诉你实际打给哪家上游；同一 group 的不同客户端可能被分到不同上游，所以合并质量会有波动，验收以「结构保留 + 两边内容都在」为准，不追求逐字一致。
- 单次合并约 2.7 秒（68 字冲突、`max_tokens` 约 800）。
