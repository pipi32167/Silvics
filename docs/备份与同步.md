# 备份与同步

文档状态：实现完成，未合并主分支。对应分支 `feat/vault-sync`。

## 1. 一句话

笔记的真相层是 vault 目录里的 Markdown 文件；sqlite 只是本机索引。备份 = 这份目录，同步 = 用 git 搬它。

## 2. 为什么不是备份 sqlite

| 数据 | 位置 | 能否从正文重建 | 必须进 vault |
| --- | --- | --- | --- |
| `note.body` | note 表 | —— | 是（真相层） |
| `note.title` / `status` | note 表 | 否 | 是 |
| `alias.name` | alias 表 | 否 | 是 |
| `mention.dismissed` | mention 表 | 否 | 是（按目标 id 存） |
| `link` / `tag` / `note_fts` | 索引表 | 是 | 否 |

两个最容易漏的：**别名**和**已忽略的提及**都不在正文里。只导出 `.md` 会丢。

不备份 sqlite 的三个理由：WAL 下直接拷文件会拿到半写状态；二进制不能 diff、不能单篇恢复；备份索引等于备份缓存，还会在恢复时制造「边和正文不一致」。

## 3. 目录与格式

```text
<vault>/
  notes/<id>.md        真相层
  manifest.json        条数与每篇哈希，用于校验
  .base/<id>.md        上次同步的版本，三方合并的 base（不进 git）
  .conflicts/          合并不了的两份原文（不进 git）
  .trash/              远端删除但本地有改动而保留下来的副本（不进 git）
  .gitignore
```

frontmatter 是 YAML 子集，只写字面量与列表：

```yaml
---
schema: 1
id: n179548881063712xi88u
title: 稀疏重复优于集中突击
status: evergreen
created: 2026-11-24T03:28:15.123Z
updated: 2026-11-24T03:28:15.123Z
aliases:
  - 遗忘规律
dismissed:
  - n1795488810644ej713s
---
正文……
```

三条硬要求：

1. **文件名用 id，不用标题。** 标题会改名，用标题做文件名会产生海量 rename。
2. **幂等。** 同样内容导出两次，字节完全一致；内容没变时一个字节都不碰（否则 git 天天全量 diff）。
3. **原子写。** 写临时文件再 `replaceItemAt`。

## 4. 两条不许违反的规则

**导出只写不删。** 库里空了不能连带清空 vault —— 一次误操作会把备份一起干掉。删除笔记时由 `removeFromVault(id:)` 显式删文件。

**绝不让 git 做合并。** `git merge` 会把 `<<<<<<<` 写进正文，污染内容，也会让 `[[ ]]` 与 `#标签` 的扫描结果错乱。合并一律自己算，git 只收一个已经解决干净的提交。

## 5. 同步流程

```text
1. 收编：vault 里有、库里没有的笔记 → 直接导入      ← 换机器/库丢了靠这一步自动恢复
2. 导出：库 → vault（只写不删）
3. 首次：git init + remote add + commit + push -u
4. fetch
5. 落后 0：需要就 push，结束
6. 落后 >0：逐个文件解决，然后提交合并
```

「逐个文件解决」的判定顺序：

| 情况 | 处理 |
| --- | --- |
| 正文相同 | 元数据取并集（别名、忽略项、时间取极值），有变化才写 |
| 本机没改（== base） | 取远端 |
| 远端没改（== base） | 保留本机 |
| 两边都改、标题也不同 | 冲突，人工。留档，保留本机 |
| 两边都改、标题相同 | `LineMerge` 三方合并；干净则采信，否则留档 + 保留本机 |
| 远端删除、本机没改 | 跟着删，先写一份到 `.trash/` |
| 远端删除、本机改过 | 保留本机 + 提示 |
| 本机删除、远端改过 | 复活远端版本（宁可多留） |

提交顺序（踩过）：先把合并结果提交成普通提交，工作区干净了才 `git merge -s ours --no-commit`，再 `commit`。反过来 `git merge` 会因为暂存区有改动而失败，历史里就没有远端那个父提交，`behind` 永远归不了零。

## 6. 冲突合并

`EditorKit/LineMerge.swift` 是 diff3：算 base→ours 与 base→theirs 的 LCS，切改动段，段不重叠就都保留，重叠就报冲突。行数乘积超过 400 000 放弃。

冲突时**不写冲突标记**，保留本机版本，把远端与本地两份原文写进 `.conflicts/`。

## 7. 校验

「校验」检查四件事：manifest 与文件集一致、每篇正文哈希与 manifest 一致、库里条数与 manifest 一致、与远端没有领先/落后。任一项不对就列出来。

## 8. 已踩的坑

1. **`TextNormalizer.bodyHash` 原来用 Swift `Hasher`**，每进程随机加盐，跨进程永远对不上。已改 SHA256。
2. **`MentionIndex.rebuildAll` 原来会清掉 `dismissed`**，重建一次索引就丢用户的忽略决定。已改为重建前保存、重建后回填。
3. **`git` 的输出不能当结果。** `git remote get-url` 失败时会把 `error: No such remote` 写进 stdout，拿输出判空会误判成「有远端」。一律看退出码。
4. **GUI App 拿不到终端里的 `ssh-agent`。** 必须显式 `GIT_SSH_COMMAND="ssh -i <私钥> -o BatchMode=yes"`。
5. **窗口自绘抓不到 SwiftUI 的 Text 层**，本机又没有真实显示会话（`screencapture` 出全黑）。面板观感证据改用 `ImageRenderer` 离屏渲染；`ImageRenderer` 画不出 `TextField` 的内容，只证明布局。
